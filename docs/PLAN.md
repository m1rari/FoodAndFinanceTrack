## Этап 1 — Каркас, авторизация, ручной ввод `[x]`

**Цель:** рабочий скелет: Mini App открывается, пользователь авторизован, может вручную вести операции и видеть отчёт за месяц.

> Реализовано. Осталось необязательное кэширование `initData` и живой smoke-тест `docker compose up` (движок Docker на машине разработчика не запущен).

### Инфраструктура
- [x] Создать структуру репозитория (`api/`, `web/`, `docs/`, `proxy/`, `docker-compose.yml`, `Caddyfile`, `.env.example`).
- [x] `docker-compose.yml`: сервисы `proxy` (Caddy), `api`, `db` (postgres:16-alpine) с `mem_limit`/`cpus` и лимитами логов (`x-logging`).
- [x] Multi-stage `api/Dockerfile` (`sdk` → `aspnet:8-alpine`, non-root).
- [x] `proxy/Dockerfile`: сборка фронтенда (node) → отдача статики Caddy.
- [x] `.env.example` с `DOMAIN`, `DB_PASSWORD`, `OPENCODE_GO_KEY`, `BOT_TOKEN`.
- [x] `.gitignore` и `.dockerignore`.

### Backend
- [x] Solution: `Api`, `Application`, `Domain`, `Infrastructure` + тестовый проект.
- [x] Подключить EF Core + Npgsql, `AppDbContext`, строка подключения из env.
- [x] Миграции: `users`, `accounts`, `categories`, `transactions` (+ задел `receipts`, `receipt_items`, `food_logs`, `category_rules`).
- [x] Эндпоинт `POST /api/auth/telegram`: валидация `initData` (HMAC), upsert пользователя.
- [x] Middleware `TelegramInitDataMiddleware`: проверка `initData` на каждом защищённом запросе.
- [ ] Кэширование `initData` по `userId` (отложено — не критично для v1).
- [x] CRUD: `GET/POST /api/transactions`, `PATCH /api/transactions/{id}` с фильтрами (период, категория, тип).
- [x] `GET /api/categories`, сидирование системных категорий (`is_system`) через миграцию.
- [x] `GET /api/reports/summary` — свод по категориям за период.
- [x] Глобальный обработчик ошибок (ProblemDetails), CORS.
- [x] Юнит-тесты (валидатор initData, сервисы), 11 тестов зелёные.

### Frontend
- [x] Скаффолд React + Vite + TypeScript, подключить `@telegram-apps/sdk`.
- [x] Тема через CSS-переменные Telegram (`--tg-theme-*`).
- [x] Авторизация: `initData` из SDK → `POST /api/auth/telegram`, заголовок `X-Telegram-Init-Data` на всех запросах.
- [x] Экран списка операций за текущий месяц.
- [x] Форма ручной операции (доход/расход, сумма, категория, комментарий).
- [x] Экран дашборда: доходы/расходы и разбивка по категориям за месяц.
- [x] `npm run build` и `npm run lint` — без ошибок и предупреждений.

### Definition of Done
- [x] Приложение открывается из бота, авторизуется автоматически.
- [x] Можно вручную добавить доход/расход и увидеть их в списке и в отчёте за месяц.
- [x] `docker compose config` валиден; `dotnet publish` собирается.
- [ ] Живой `docker compose up --build` (нужен запущенный Docker-движок).

## Этап 2 — Загрузка чеков (без AI) `[x]`

**Цель:** принять фото чека, сохранить оригинал, показать статус обработки. AI пока заглушка.

- [x] Миграции: `receipts`, `receipt_items` (созданы как задел в `InitialCreate`).
- [x] Хранилище файлов: volume `uploads`, абстракция `IFileStorage` (локальный провайдер `LocalFileStorage`).
- [x] `POST /api/receipts` — загрузка (multipart), лимит 8 МБ, определение типа по magic bytes, сохранение оригинала.
- [x] `GET /api/receipts/{id}` — статус и данные разбора.
- [x] `GET /api/receipts/{id}/image` — отдача оригинала (через заголовок `X-Telegram-Init-Data`).
- [x] `PATCH /api/receipts/{id}/items/{itemId}` — правка позиции.
- [x] `POST /api/receipts/{id}/items` — ручное добавление позиции (работа без AI, обязательное правило 8).
- [x] Заглушка `IReceiptAnalyzer` (`StubReceiptAnalyzer`) — чек переходит в `NeedsReview` для ручного разбора.
- [x] Сжатие изображения на клиенте перед отправкой (`utils/image.ts`).
- [x] UI: загрузка/съёмка фото (вкладка «Чек»), экран статуса, правки и добавления позиций.

**DoD:** чек загружается, оригинал лежит в volume, статус отображается, позиции можно править; AI не задействован.

> Обработка анализатором пока синхронная (заглушка мгновенна). На Этапе 3 её заменит реальный AI и фоновый статус `pending` → `processed`/`failed`.

## Этап 3 — AI-анализ чеков `[x]`

**Цель:** автоматический разбор чека в структурированный JSON с валидацией.

- [x] Реализовать `IReceiptAnalyzer` поверх OpenCode Go API (vision) + OCR-слой (`OpenCodeGoReceiptAnalyzer`).
- [x] Промпт со strict JSON schema; ответ без свободного текста.
- [x] Сохранять `raw_ocr_text` и `ai_raw_response` (jsonb).
- [x] Валидация: сумма позиций ≈ итог чека (допуск на округление), обязательные поля (`ReceiptProcessor`).
- [x] Порог `confidence` → статус `needs_review` с пометкой в UI.
- [x] Асинхронная обработка: загрузка → `pending` → очередь (`IReceiptProcessingQueue`) → фон (`ReceiptProcessingWorker`) → `processed`/`failed`.
- [x] Автосоздание `transactions` из подтверждённого чека (`source = receipt`, `POST /api/receipts/{id}/confirm`).
- [x] Поведение при недоступности AI: статус `failed`, возможность ручного ввода (при пустом ключе — заглушка и `needs_review`).
- [x] UI polling статуса обработки, пометки низкой уверенности, кнопка «Провести в операции».

**DoD:** фото чека → через N секунд готовые позиции с категориями и статусом; низкая уверенность помечена; сырой ответ сохранён.

> Проверено на боевом сервере с реальным ключом: фото чека → `processed` с позициями и категориями; подтверждение
> создаёт операции (`source = receipt`); повторный confirm и правки после confirm → 400. При пустом ключе
> используется `StubReceiptAnalyzer` — чек уходит в `needs_review` с ручным вводом (правило 8).

## Этап 4 — Автокатегоризация и обучение

**Цель:** запоминать правки пользователя и применять правила автоматически.

- [ ] Миграция `category_rules`.
- [ ] `POST /api/category-rules` — создание правила (`match_pattern` → `category_id`).
- [ ] Движок сопоставления: при классификации сначала `category_rules`, затем AI.
- [ ] Обучение: при правке категории позиции/транзакции предлагать/создавать правило.
- [ ] UI управления правилами (просмотр, удаление, редактирование).
- [ ] Кейс «Евроопт = Продукты» применяется автоматически в следующий раз.

**DoD:** повторный чек из того же магазина классифицируется без AI/с правкой в 1 клик.

## Этап 5 — Фото блюд, калории/БЖУ `[x]`

**Цель:** оценка калорийности и состава питания по фото.

- [x] Миграция `food_logs` (базовая — в `InitialCreate`; диапазоны БЖУ — `AddFoodLogMacroRanges`).
- [x] `POST /api/food-logs` — загрузка фото, платформенная обработка как у чеков (та же очередь/воркер).
- [x] `IFoodImageAnalyzer` поверх OpenCode Go API (`OpenCodeGoFoodImageAnalyzer`).
- [x] Ответ строго диапазонами калорий/БЖУ + пометка «оценка».
- [x] `GET /api/food-logs/{id}` — результат; `GET /api/food-logs?from&to` — дневник.
- [x] Коррекция калорий/БЖУ/названия/времени пользователем (`PATCH /api/food-logs/{id}`).
- [x] UI: вкладка «Питание», дневник по дням с итогами, добавление блюда, экран блюда с коррекцией и удалением.
- [x] Пользовательский контекст к фото блюда: поле при загрузке и в карточке, передаётся в промпт AI; повторный анализ с контекстом (`POST /api/food-logs/{id}/reanalyze`).
- [x] Поп-ап «+ Блюдо»: «Новое» (фото и/или описание в одной карточке), разделы «Избранные» и «Недавние» блюда (`saved_dishes`) с быстрым добавлением в дневник.

**DoD:** фото блюда → карточка с диапазоном калорий/БЖУ и пометкой «оценка»; значения можно скорректировать.

> Общий vision-клиент `OpenCodeGoVisionClient` теперь используется и чеками, и блюдами. См. ADR-016.

## UX-редизайн под MiniApp `[x]`

- [x] Вкладки Операции / Добавить / Отчёты; «Добавить» — хаб (вручную / камера / галерея) без автофокуса.
- [x] Операции по дням (заголовок дня + итоги); чек — одна строка «Покупка» → карточка покупки.
- [x] Фильтры: чипы пресетов (День/Неделя/Месяц/Период) + bottom-sheet (тип, категория, свой диапазон), по умолчанию текущий месяц.
- [x] Карточка покупки: товары списком, редактор товара в bottom-sheet, проведение в операции.
- [x] Клавиатура: убран автофокус, тап по фону и Enter закрывают клавиатуру/форму.

- [x] Сопоставление ручной операции с чеком (совпадение по сумме ±0.01 и дате ±1 день, «Прикрепить» / «Это разные»).
- [x] Приём чеков в чате бота: фото → webhook → распознавание → ответ «✅ Чек добавлен …» / «⚠️ Проверьте в приложении».
- [x] Раздел «Неразобранные покупки» на экране Операций: невыведенные чеки (в т.ч. из бота) видны и открываются в карточку покупки.
- [x] Бот: кнопки «Чек»/«Еда», приём фото и текстового описания для обоих режимов, голосовые — вежливый отказ с просьбой прислать фото/текст.

> См. ADR-012 (UX), ADR-013 (сопоставление), ADR-014 (бот).

## Этап 7 — Оптимизация и эксплуатация

- [ ] Проверить и зафиксировать `mem_limit`/`cpus` для всех сервисов.
- [ ] Лимиты логов Docker в compose + `daemon.json` (max-size 10m, max-file 3, compress).

- [ ] Бэкап volume `pg_data` (минимум раз в сутки, ротация).
- [ ] Мониторинг/очистка диска и TTL для `pending`/`failed` файлов.
- [ ] Оценка: общий вес образов без Postgres ≤ ~300–400 МБ.
- [ ] По необходимости миграция `uploads` → MinIO.

**DoD:** ресурсы и логи под контролем, есть бэкапы и мониторинг диска, соблюдены нефункциональные требования (§10).
