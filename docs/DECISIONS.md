## Принятые решения (из ТЗ)

### ADR-001: PostgreSQL как основное хранилище
- **Дата:** 2026-09-25
- **Статус:** принято
- **Контекст:** реляционные данные, суммы, отчёты.
- **Решение:** PostgreSQL + EF Core; деньги — `numeric(12,2)`.
- **Последствия:** миграции EF обязательны; тюнинг под малый VPS.

### ADR-002: AI через абстракции
- **Дата:** 2026-09-25
- **Статус:** принято
- **Контекст:** провайдер AI может смениться.
- **Решение:** `IReceiptAnalyzer` / `IFoodImageAnalyzer`; провайдер (OpenCode Go) только в Infrastructure.
- **Последствия:** контроллеры не знают о провайдере; простое тестирование через mock.

### ADR-003: Redis не подключаем в v1
- **Дата:** 2026-09-25
- **Статус:** принято
- **Контекст:** экономия ресурсов сервера.
- **Решение:** фоновая обработка встроенными средствами; Redis только при реальной потребности в очереди.
- **Последствия:** меньше контейнеров и RAM; пересмотреть при росте нагрузки.

### ADR-004: Файлы — volume, позже MinIO
- **Дата:** 2026-09-25
- **Статус:** принято
- **Контекст:** старт на одном небольшом VPS.
- **Решение:** оригиналы в volume `uploads`, абстракция `IFileStorage` для будущей замены на MinIO.
- **Последствия:** следить за диском, TTL для `pending`/`failed`.

### ADR-005: Оригиналы изображений хранятся всегда
- **Дата:** 2026-09-25
- **Статус:** принято
- **Контекст:** повторный анализ, отладка.
- **Решение:** не удалять исходники после обработки.
- **Последствия:** рост объёма, нужен мониторинг диска.

### ADR-006: Аутентификация — initData на каждом запросе (без JWT)
- **Дата:** 2026-09-25
- **Статус:** принято
- **Контекст:** ТЗ §9 требует проверять `initData` строго на сервере на каждом запросе.
- **Решение:** `POST /api/auth/telegram` валидирует `initData` и upsert-ит пользователя; все защищённые запросы несут заголовок `X-Telegram-Init-Data`, который проверяется middleware через HMAC на каждом запросе. JWT не используется.
- **Последствия:** проще и строго по ТЗ; нет refresh-токенов и хранения сессий. При росте нагрузки добавить кэш `initData → userId`.

### ADR-007: Reverse-proxy собирает и отдаёт статику фронтенда
- **Дата:** 2026-09-25
- **Статус:** принято
- **Контекст:** ТЗ §8.1: proxy отдаёт статику фронта.
- **Решение:** `proxy/Dockerfile` multi-stage: `node:22-alpine` собирает `web/dist`, финальный `caddy:alpine` отдаёт статику из `/srv` и проксирует `/api/*` на `api:8080`. Отдельного web-контейнера нет.
- **Последствия:** на один контейнер меньше (экономия RAM); фронт и прокси релизятся одним образом. Изменение только фронта требует пересборки образа proxy.

### ADR-008: Линтер фронтенда — oxlint
- **Дата:** 2026-09-25
- **Статус:** принято
- **Контекст:** шаблон Vite 8 по умолчанию использует `oxlint`.
- **Решение:** оставляем `oxlint` (`npm run lint`), без добавления ESLint.
- **Последствия:** быстрая проверка, меньше зависимостей. Соблюдаем нулевое число предупреждений (React Hooks/Compiler правила).

### ADR-009: Приём чеков — ручной разбор без AI на Этапе 2
- **Дата:** 2026-09-26
- **Статус:** принято
- **Контекст:** правило 8 — приложение работает без AI; на Этапе 2 реальный анализ ещё не реализован.
- **Решение:** `POST /api/receipts` принимает multipart ≤ 8 МБ, тип определяется по magic bytes (JPEG/PNG/WebP), оригинал сохраняется через `IFileStorage`. `StubReceiptAnalyzer` не извлекает данные → чек получает статус `NeedsReview`; позиции добавляются/правятся вручную (`POST`/`PATCH .../items`), итог пересчитывается по позициям, статус → `Processed`.
- **Последствия:** полный пользовательский сценарий проверяем уже без AI; на Этапе 3 заглушка заменяется реализацией `IReceiptAnalyzer` и фоновой обработкой. Итог чека (`TotalAmount`) на Этапе 2 — сумма позиций, а не значение с чека.

### ADR-010: AI-анализ чеков — OpenCode Go (OpenAI-совместимый) + фоновая очередь
- **Дата:** 2026-09-26
- **Статус:** принято
- **Контекст:** ТЗ §7 требует structured JSON, изоляцию провайдера и асинхронный анализ; ADR-003 — без Redis.
- **Решение:** провайдер вызывается через `IReceiptAnalyzer`; реализация `OpenCodeGoReceiptAnalyzer` шлёт `POST {BaseUrl}/chat/completions` (OpenAI-совместимо, `image_url` с base64 data URL, Bearer, собственный User-Agent, обязательный заголовок `x-opencode-session` = id чека для роутинга/кэша). Промпт со strict JSON schema + `response_format: json_object` (с ретраем без него при 400). OCR выполняет сама vision-модель, распознанный текст пишется в `raw_ocr_text`. Очередь — `Channel<Guid>` (`IReceiptProcessingQueue`) + `BackgroundService` (`ReceiptProcessingWorker`) с восстановлением `pending`-чеков при старте. Вся валидация и маппинг категорий — в `ReceiptProcessor`.
- **Последствия:** при перезапуске не потерянные задачи восстанавливаются из БД; провайдер заменяется без правки Application; при пустом `OPENCODE_GO_KEY` используется `StubReceiptAnalyzer` → `needs_review`. Порог — `Ai:ConfidenceThreshold` (env `AI_CONFIDENCE_THRESHOLD`), модель — `OpenCodeGo:Model` (env `AI_MODEL`).

### ADR-011: Подтверждение чека и создание операций
- **Дата:** 2026-09-26
- **Статус:** принято
- **Контекст:** нужен явный момент «чек подтверждён», чтобы не заводить операции дважды и не редактировать подтверждённое.
- **Решение:** `POST /api/receipts/{id}/confirm` создаёт по `Transaction` на каждую позицию (`source = receipt`, `receiptId`, категория позиции, дата — `purchase_date` или `created_at`). Факт подтверждения определяется наличием транзакций с этим `receipt_id` (без новой колонки/миграции). После подтверждения правки позиций запрещены (400).
- **Последствия:** не нужен новый столбец `confirmed_at` и миграция; повторный `confirm` возвращает ошибку. Редактирование операций после проведения — через обычный `PATCH /api/transactions`.

### ADR-012: UX-редизайн под MiniApp — дни, покупки, фильтры
- **Дата:** 2026-09-26
- **Статус:** принято
- **Контекст:** плохой UX на мобильном: автофокус суммы вызывает клавиатуру, операции не сгруппированы, чек дробится на операции, нет фильтров.
- **Решение:**
  - Вкладки: **Операции / Добавить / Отчёты**. «Добавить» — хаб (вручную / камера / галерея), без автофокуса.
  - Операции группируются **по дням** (заголовок дня + итоги), а операции с `receipt_id` — в одну строку **«Покупка»** с переходом на карточку покупки. В БД по-прежнему операции по товарам — отчёты остаются детальными.
  - Фильтры — чипы пресетов (День/Неделя/Месяц/Период) + `BottomSheet` (тип, категория, свой диапазон); по умолчанию текущий месяц.
  - Редактор товара и фильтры вынесены в `BottomSheet` вместо длинных инлайн-форм.
  - Клавиатура: убран `autoFocus`; тап по фону закрывает клавиатуру (глобальный blur в `App`); у полей `enterKeyHint="done"`; Enter сохраняет форму.
- **Последствия:** добавлен `receiptMerchantName` в `TransactionDto` (join на `receipts`) для заголовка покупки. Сопоставление ручной операции с чеком и приём чеков ботом — следующие этапы (см. ADR-013/014).

### ADR-013: Сопоставление ручной операции с чеком
- **Дата:** 2026-09-26
- **Статус:** принято
- **Контекст:** пользователь мог вручную внести покупку, а потом загрузить чек — иначе получится дубль.
- **Решение:** `GET /api/receipts/{id}/matches` ищет ручные расходы (`source = manual`, без `receipt_id`) с суммой ±0.01 и датой ±1 день от даты покупки/создания чека. `POST /api/receipts/{id}/link/{transactionId}` прикрепляет чек к существующей операции (проставляет `receipt_id`) — операция считается проведённой, дубли не создаются. AI не используется: детерминированный матчинг, подтверждает пользователь.
- **Последствия:** чек может быть либо «прикреплён» к ручной операции, либо проведён отдельной покупкой через `confirm`. После прикрепления правки позиций запрещены (как после confirm).

### ADR-014: Приём чеков в чате бота через webhook
- **Дата:** 2026-09-26
- **Статус:** принято
- **Контекст:** хочется скидывать чек в чат и получать результат, не открывая MiniApp.
- **Решение:** `POST /api/telegram/webhook` (путь исключён из проверки `initData`), защищён заголовком `X-Telegram-Bot-Api-Secret-Token` (`Telegram:WebhookSecret`). Бот скачивает фото (`getFile` + `/file/bot…`), создаёт пользователя и чек с `telegram_chat_id`. Обработка — в существующей фоновой очереди; после неё `ReceiptProcessor` отправляет результат в чат (`sendMessage`). Регистрация webhook — `TelegramWebhookSetup` (IHostedService) при заданных `BotToken` + `PublicBaseUrl`.
- **Последствия:** добавлена колонка `receipts.telegram_chat_id` (миграция). Нужны env `PUBLIC_BASE_URL` и `TELEGRAM_WEBHOOK_SECRET`. Если AI недоступен — бот пишет «добавьте вручную».

### ADR-015: Удаление покупки
- **Дата:** 2026-09-26
- **Статус:** принято
- **Контекст:** нужна возможность удалять покупки — и неразобранные, и уже проведённые.
- **Решение:** `DELETE /api/receipts/{id}`. Удаляются чек, позиции и оригинал изображения (`IFileStorage.DeleteAsync`). Операции с этим `receipt_id` обрабатываются по источнику: созданные из чека (`source = receipt`) удаляются, а прикреплённые вручную (`source = manual`) — отвязываются (`receipt_id = null`) и сохраняются. Из UI — кнопка «Удалить покупку» с подтверждением в карточке покупки (доступна и для неразобранных из раздела «Неразобранные покупки», и для проведённых из списка операций).
- **Последствия:** удаление проведённой покупки убирает её операции из отчётов; ручная операция, к которой был прикреплён чек, остаётся. Оригинал фото удаляется вместе с покупкой (отступление от «хранить всегда» осознанное — по явному действию пользователя).

### ADR-016: Анализ блюд — общий vision-клиент, диапазоны, дневник
- **Дата:** 2026-09-26
- **Статус:** принято
- **Контекст:** Этап 5 требует оценку калорий/БЖУ по фото диапазонами; ТЗ — «питание всегда диапазоном, с пометкой оценка».
- **Решение:** HTTP-обвязка OpenCode Go вынесена в `OpenCodeGoVisionClient` (Bearer, UA, `x-opencode-session`, `response_format` с ретраем) — переиспользуется `IReceiptAnalyzer` и `IFoodImageAnalyzer`. Реализация `OpenCodeGoFoodImageAnalyzer` просит strict-JSON с `*_min`/`*_max` по калориям и БЖУ. В `FoodLog` хранятся min/max для калорий и каждого макро, плюс `protein_g/fat_g/carbs_g` — середина диапазона (для быстрых итогов). Обработка — отдельная очередь/воркер по образцу чеков. Пользователь может править значения; статус `needs_review` при низком `confidence` или пустом ответе.
- **Последствия:** добавлена миграция `AddFoodLogMacroRanges` (6 колонок). UI — вкладка «Питание» с дневником по дням и итогами в виде диапазонов и пометкой «оценка». Связка «траты на еду vs калории» — Этап 6.

### ADR-017: Пользовательский контекст к фото блюда
- **Дата:** 2026-09-26
- **Статус:** принято
- **Контекст:** по одному фото AI иногда неверно определяет блюдо/порцию; пользователь может подсказать.
- **Решение:** поле `food_logs.user_context` (миграция `AddFoodLogUserContext`), задаётся при загрузке (`context` в multipart) и редактируется в карточке (`PATCH`). Контекст добавляется в user-часть промпта vision-модели. `POST /api/food-logs/{id}/reanalyze` сбрасывает статус в `pending`, при необходимости обновляет контекст и заново ставит в очередь.
- **Последствия:** загрузка блюда на клиенте теперь двухшаговая (фото → bottom-sheet с контекстом → «Распознать»); в карточке — «Распознать заново» и «Распознать с этим контекстом».
